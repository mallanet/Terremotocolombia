# Platform Operability - Plan

**Origin plan:** [Multi-Incident Platform Migration - Plan](./2026-08-12-001-refactor-multi-incident-platform-plan.md) (`docs/plans/2026-08-12-001-refactor-multi-incident-platform-plan.md`). That plan (the "base plan") builds the multi-incident platform through Phases A-F plus U27 (Family reunification) and cuts Colombia production over to it.

**Phase 0 reconciliation (2026-08-21):** current `origin/main` is `83b7c16`. The entry gate is unchanged and is not satisfied: U21/U22 are not complete, and no second-incident driver is named. U23–U33 stay parked. U30 repository evidence (NULL organization, wildcard system role, seed superadmin, single global user role, unscoped API keys, admin BFF) still holds at `83b7c16`. Live Colombia now also has reconstruction-campaign administration and official deceased imports; those tenant-data surfaces stay out of the Mallanet operations console.

This plan extracts that base plan's Phase G and Phase H units — U23, U24, U25, U26, U28, U29, U30, U31, U32, U33 — into a standalone follow-up plan. U27 stays in the base plan: it is not an operability unit, and U26's activation step depends on it. Every base-plan unit U0-U22 and U27 was mechanically verified to have no dependency on any unit in this plan.

## Goal Capsule

- **Objective:** make the multi-incident platform the base plan builds operable — a tenant/incident provisioning control plane, hazard-signal detection that proposes reviewable incident candidates, one runtime-configured public frontend serving every approved deployment, checkpointed rapid-response communications provisioning, organization authorization and governance separate from Mallanet platform authority, a Mallanet operations console with privileged approvals and support access, and governed cross-tenant analytics — all on the platform the base plan builds, without weakening any base-plan guarantee. These surfaces also provide the governed channels, response workspaces, safety casework, policy approvals, and health controls consumed by the base plan's U35 volunteer coordination intelligence.
- **Authority:** this document owns the product and technical decisions for its own units (U23, U24, U25, U26, U28, U29, U30, U31, U32, U33). Requirements, Key Decisions, Key Technical Decisions, and Acceptance Examples cited here by ID (e.g. "R23", "KTD30") are defined in this document unless annotated otherwise. An ID cited here but not defined here (e.g. R7-R10, KTD5, KTD12, KD3) is owned by the base plan at `docs/plans/2026-08-12-001-refactor-multi-incident-platform-plan.md` — see "Cross-document citations" under Planning Contract. Repo conventions (`AGENTS.md`, `CLAUDE.md`) govern where this plan is silent, on the same terms as the base plan.
- **Entry gate:** work under this plan begins only after both of the following hold. (1) The base plan's U21 (production-scale rehearsal and platform cutover) and U22 (compatibility retirement and old-repo closure) are complete — the platform repo is the production release source and the old repo is read-only. (2) A concrete second-incident driver is named: a committed incident, a committed timeline, or a funding decision that makes provisioning a second tenant a real near-term event, not a hypothetical one. Building a provisioning console, a hazard detector, or an organization-governance model against a platform that has only ever run one tenant — with no second tenant on the horizon — risks designing against imagined requirements. Until both conditions hold, this plan is parked; the base plan's Scope Boundaries records it as deferred follow-up work.
- **Stop conditions:** mirror the base plan's stop conditions, applied to this plan's units — a schema change that cannot follow the expand-first/manual/before-code discipline; a cross-incident isolation test failure; evidence that a settled decision cannot work (report it, do not improvise around it); any change that would break a public URL, make a non-additive change to a public payload, or weaken a base-plan tenant-isolation guarantee.
- **Tail ownership:** work lands through PRs against the platform repo, on the same release-control discipline U0 established in the base plan (immutable-SHA promotion, production approval, independently promotable artifacts). U23's provisioning ledger and U32's operation ledgers own the operational tail for this plan's own capabilities the way U19 owned source synchronization for the base plan's cutover.

## Product Contract

### Summary

The base plan turns Colombia into the platform's first tenant: shared contracts, tenant-scoped records, modules/providers/catalogs, and a tenant-scoped Family Search all exist by the time this plan starts. None of that lets Mallanet actually run a second incident. This plan adds the operability layer on top: operators can provision and preview a new organization/incident from desired state instead of hand-cloning a repository; versioned hazard observations can produce human-reviewed incident candidates instead of requiring a human to notice an earthquake; one immutable public frontend artifact can serve every approved deployment/incident combination at runtime instead of each deployment needing its own build; a response's communications (email, SMS, WhatsApp, inbound forms) can launch through a checkpointed, auditable provisioning ledger instead of ad hoc setup; and Mallanet's nonprofit-wide platform authority stays a separate, audited trust domain from each organization's own governance and each incident's own command structure, with cross-tenant analytics that never leaks person-level data.

### Problem Frame

By the end of the base plan's Phase F, the platform is real but still effectively single-tenant in practice: Colombia is the only organization/incident that has ever existed on it. Four gaps keep it from being operable for a second incident. Provisioning still means cloning a template repository and hand-editing configuration — there is no idempotent, auditable, resumable way to stand up an organization and an incident. Hazard awareness is entirely manual — nothing watches USGS or any other source and proposes a reviewable incident candidate; a human has to notice a disaster and start provisioning by hand. The public frontend is a build-time artifact keyed to one deployment configuration, so a second incident needs its own frontend build and deploy, not a runtime configuration change. And authorization is still a single global role with a nullable organization column and wildcard system-role behavior — there is no safe way to give one human independent access to two organizations, or to give Mallanet's own nonprofit staff a lifecycle/release console without turning platform credentials into ambient tenant-data access. This plan is deliberately sequenced after the base plan's cutover and gated on a named second-incident driver (see Goal Capsule) so that these capabilities are built against a real second tenant's requirements, not a hypothetical one.

### Requirements

**Tenant and incident operations**

- R23. An operator can provision an organization and one or more incidents through an idempotent, auditable dry-run/apply workflow. Organization and incident are separate lifecycle objects: one organization can operate several incidents over time.
- R24. Lifecycle states are explicit and independently authorized. Organization: `pending | active | suspended | archived`. Incident: `draft | provisioning | preview | ready | active | paused | closed | archived | failed`. Deployment/hostname: `reserved | verification_pending | preview | active | disabled | released`. Only an approved transition can attach public traffic, enable producers, or send notifications.
- R25. Provisioning validates and records deployment hostnames, DNS/Cloudflare ownership, CORS and Access configuration, secrets and provider readiness, module profiles, catalogs, geography, emergency contacts, memberships, API keys, queues, schedules, rate-limit namespaces, storage/cache epochs, the base plan's Upstash cache resource/policy/budget/credential references, and rollback targets.
- R26. Every provisioning step is resumable and convergent. Re-running the same desired configuration does not duplicate resources. A failed step leaves the incident non-public, identifies completed/compensating steps, and can resume or roll back safely.

**Hazard signals and incident candidates**

- R27. Hazard-source adapters normalize provider observations into versioned canonical observations with source identity, provider event ID, hazard type, geometry, occurrence/update time, severity fields, provenance, raw checksum/object reference, schema version, and ingestion build SHA.
- R28. USGS is the first earthquake adapter. Additional approved sources plug into the same port. The platform tracks source freshness, latency, errors, schema drift, replay cursor, and circuit state; a stale or failed source is visible and never treated as evidence that an event ended.
- R29. A deterministic correlator groups observations into canonical hazard events using source IDs, hazard type, time, distance, geometry, administrative region, and revision history. It supports merge, split, supersede, withdraw, and replay without duplicate public incidents.
- R30. Detection creates an auditable incident candidate, not a public incident. Candidate states are `detected | correlating | review_required | approved | rejected | suppressed | merged | expired | provisioning`. Initial releases require a human with a dedicated capability to approve provisioning and activation.
- R31. Thresholds and routing rules are versioned per monitored geography and hazard type. Each decision records the rule version, input observation IDs, reasons, computed values, and operator actions so historical feeds can reproduce the outcome.
- R32. Approval converts a candidate into a draft incident or links it to an existing incident. Activation then follows R23-R26 and cannot bypass preview, readiness, tenant-isolation, provider, notification, and rollback gates.
**Runtime deployments and communications**

- R45. One immutable public frontend artifact can serve several approved deployments. It resolves a trusted hostname to a signed/versioned deployment bootstrap that supplies organization identity, deployment identity, allowed/default incidents, branding, locale, modules, public navigation, API authority, PWA metadata, map/catalog revisions, and cache epoch. Unknown or incomplete hostnames fail closed; host headers, query parameters, or client-provided incident IDs never establish authority.
- R46. A deployment can expose one incident or an approved collection of incidents. Every request and client cache still resolves one explicit `TenantScope` unless it uses a separately contracted, privacy-reviewed cross-incident read projection. Assignment, ordering, default/featured incident, public visibility, and deployment navigation are configuration revisions with preview and rollback—not frontend code forks.
- R47. Runtime identity is safe across CDN, HTML, assets, service workers, IndexedDB, local storage, and open tabs. Cache and storage namespaces include deployment/config/incident identity as applicable; activation rotates an epoch and preserves a compatible previous generation for the rollback window. A hostname reassignment cannot display or submit data for its previous incident.
- R48. Response launch includes an incident-scoped channel registry and checkpointed provisioning for owned email/SMS/WhatsApp Business messaging endpoints, public WhatsApp group/community invitation links, social accounts, inbound forms/webhooks, and any approved partner channel. Automated adapters and human/external steps use the same desired-state ledger; unsupported provider actions enter `waiting_external` with exact verification instructions.
- R49. Channel activation is distinct from resource creation. Each channel records owner, provider/external identity, public address, purpose, audience, inbound/outbound direction, moderation/escalation owner, consent/template status, secret reference, environment, lifecycle, health, last verification, and rollback/retirement action. Outbound or mass messaging remains off until separately approved; an optional channel failure does not block the core site.
- R50. WhatsApp is two explicit capabilities: public group/community discovery through verified invitation links, and one-to-one or template messaging through an approved WhatsApp Business Platform provider. The plan does not assume that ordinary groups/communities can be created or administered through the Business messaging API; provider capability is revalidated at implementation time and manual creation remains a first-class checkpoint.

**Administrative authority and nonprofit operations**

- R51. Administration uses a fixed scope/ancestry graph: platform owns organizations; deployment and incident are organization-owned peers; module/case scopes are incident-owned; `deployment_incidents` is an authorized visibility/configuration relation, not authority inheritance. A visible selector changes working context only within the actor's existing grants; it never grants access. Deployment is a public product/configuration boundary and incident is an operational data/workflow boundary, even when one deployment currently exposes one incident.
- R52. Grants are capability- and scope-specific, environment-specific, attributable, revocable, and optionally time-bounded. The record distinguishes the receiving `subject_principal_id`/`subject_membership_id` from `granted_by_principal_id` and audit actor; it includes capability, scope type/ID, environment, start/expiry, reason/change reference, version, and revocation. `NULL` scope never means global access. Staffing a response does not make a user an organization owner or Mallanet platform operator.
- R53. Mallanet has a distinct platform operations console for its nonprofit staff: organization/incident/deployment portfolio, candidate review, provisioning/activation ledgers, release/config/domain drift, provider/channel/source health, Queue/Cron/DLQ state, readiness, privacy/security alerts, and approved aggregate reporting. It uses platform capabilities and cannot expose tenant-sensitive detail through an organization selector shortcut.
- R54. Organization governance can manage organization membership, scoped response assignments, role templates, policies, incident/deployment configuration proposals, channel ownership, and organization-wide reporting inside that organization. Incident command can operate only its assigned response, modules, queues, content, volunteers, cases, providers, readiness, and approved communications. Platform-only actions—organization creation, domain ownership/reassignment, production activation, platform secret/config changes, or cross-organization access—remain unavailable.
- R55. High-impact operations use separation of duties and policy-controlled dual approval: public activation or hostname reassignment, mass notification, personal-data export, sensitive person/location disclosure, cross-incident person search, retention/legal-hold changes, privileged credential rotation, and final archive/hostname release. The proposer cannot satisfy an approval that policy requires from a distinct actor.
- R56. Platform support access uses an audited, time-boxed support session, not silent impersonation or a standing global tenant role. It has a ticket/reason, target scopes, read-only default, visible banner, explicit write escalation/approval, automatic expiry/revocation, and payload-minimized access events. Sensitive search terms, contacts, documents, evidence, or tokens never enter support logs.
- R57. Admin clients show organization, deployment, incident, environment, and support/elevation state persistently. Scope changes cancel in-flight work, clear or partition queries/forms/drafts, reauthorize deep links and mutations server-side, and prevent stale incident-A state from being submitted under incident B.
- R58. Cross-organization dashboards use approved aggregate projections with minimum cell-size/suppression and no person-level join path. Sensitive cross-scope queries require a named purpose, explicit platform capability, participating scopes, result limits, no-store responses, and audited access; family-person federation remains off under R43.

### Key Decisions

- KD4. **Signal detection proposes; humans activate.** During the first operating stages, no external feed can create a public incident, change public routing, enable outbound notifications, or spend provider resources. Detection produces a reviewable candidate with complete provenance. Automation can advance only to preview after an approved policy explicitly permits it. Governs R27-R32.
- KD5. **Tenant provisioning is desired-state reconciliation, not a one-shot script.** A versioned manifest plus operation ledger drives dry-run, apply, resume, and rollback. Cloud resources and database rows have stable idempotency keys and ownership tags. Governs R23-R26.
- KD6. **Public sites are runtime-configured deployments.** After U28, the same immutable public artifact serves approved hostnames and deployment-to-incident assignments through a trusted bootstrap. Per-deployment forks stop; a configuration revision and cache epoch become release inputs. Governs R45-R47.
- KD7. **Communications are provisioned resources with explicit activation.** U29 models automated providers and human/external setup in one operation ledger, but never treats creation of a WhatsApp group, social account, or messaging sender as guaranteed API automation. Governs R48-R50.

### Scope Boundaries

**Deferred to Follow-Up Work**

- A customer-facing console that lets one tenant self-select or administer unrelated organizations. U31 remains organization/response scoped; U32 is a distinct internal Mallanet operations trust domain and is not a tenant-data browser.

**Outside this product's identity**

- Automatic creation/administration of ordinary WhatsApp groups or communities unless Meta exposes and Mallanet approves a supported API at implementation time. U29 still provisions verified invitation links and approved WhatsApp Business messaging endpoints through automated or `waiting_external` steps.

### Acceptance Examples

- AE12. **Covers R23-R26.** Given an approved manifest for organization A and incident B, dry-run lists every database and Cloudflare change without mutation. Apply creates a preview deployment once. Re-running apply produces no duplicate row, route, queue, schedule, membership, or secret reference.
- AE13. **Covers R24-R26.** Given provisioning fails after DNS validation but before provider validation, the public hostname remains unattached, producers remain disabled, the ledger records the completed steps, and resume continues from the safe checkpoint after repair.
- AE14. **Covers R27-R31.** Given USGS reports an earthquake inside a monitored region, ingestion stores a canonical observation and detection creates a review candidate with the input observation and rule version. It does not create or activate a public incident.
- AE15. **Covers R28-R31.** Given a second source later reports the same earthquake with a different source ID and revised magnitude, correlation attaches it to the existing canonical hazard event and updates the candidate evidence without duplicating the candidate.
- AE16. **Covers R28.** Given the USGS feed becomes stale or changes schema, source health becomes degraded and alerts. Existing candidates and incidents remain unchanged; absence of new observations is not interpreted as cancellation.
- AE17. **Covers R29-R32.** Given an operator approves a candidate, the platform creates or links one draft incident, generates a preview, passes readiness gates, and requires a separate activation approval before public routing. Rejection or suppression is audited and prevents repeated candidate noise under the versioned suppression rule.
- AE25. **Covers R45-R47.** Given the same frontend artifact digest is served on `terremotocolombia.co` and an approved Venezuela response domain, each hostname receives its own signed deployment bootstrap and PWA/branding/API/incident configuration. Replaying either bootstrap or service-worker cache on the other hostname fails authority/digest checks and cannot read or submit the other incident's data.
- AE26. **Covers R46, R58.** Given one Mallanet deployment exposes two approved incidents, switching the public view clears incident-scoped query/offline/form state and obtains a new server-resolved scope. A cross-incident visualization calls only its named aggregate contract; it cannot follow an identifier into person-level or private incident data.
- AE27. **Covers R48-R50.** Given an incident manifest requests a WhatsApp community link, Business messaging sender, email, and SMS, supported provider resources reconcile idempotently while the manually created community remains `waiting_external` until its owner and invitation are verified. A failed optional SMS step does not attach outbound messaging, does not block the public site, and resumes without duplicating any sender/channel.
- AE28. **Covers R49, R55.** Given a verified outbound channel, an incident operator can preview a bounded audience but cannot send a broadcast. A different authorized approver approves the immutable message/template/audience digest; changing any input makes the approval stale, and a provider failure activates the stop switch without changing public routing.
- AE29. **Covers R51-R54.** Given one human belongs to organizations A and B with different roles, the same global identity resolves separate active memberships on their trusted admin hosts. An invitation, role, grant, incident, deployment, or user ID from B supplied under A cannot be read or mutated, and selecting B in the browser cannot manufacture authority.
- AE30. **Covers R52, R57.** Given a volunteer's incident-A assignment expires while their admin tab is open, the next request is denied, subscriptions and cached/draft state are cleared, and the identity can still use a separately valid organization-B membership. `/me` never emits wildcard authority.
- AE31. **Covers R53, R58.** Given a Mallanet platform operator can provision incident metadata and view suppressed portfolio health, a direct tenant report/person/case query is denied. The operator sees sensitive tenant data only through a separately approved support session with exact scope and capability.
- AE32. **Covers R55.** Given the requester proposes production hostname activation, they cannot satisfy the required activation approval. Execution accepts only the approved plan/artifact/config/readiness/rollback digests and refuses an expired, already-used, self-approved, or stale decision.
- AE33. **Covers R56-R58.** Given an organization approves a read-only support session for one incident and one hour, the operator remains the actor, sees a persistent support banner, cannot change membership/keys/secrets/deployments or query another incident, and loses access on the first request after expiry/revocation. Audit records purpose and object/result class without query text or payload.
- AE34. **Covers R54, R57.** Given an incident commander requests enabling a provider or outbound channel, the admin records a scoped change request and routes it through desired-state planning; it does not directly edit secrets, edge bindings, schedules, or production resources. Ordinary module operations that require no deployment effect remain available inside the incident workspace.

## Planning Contract

### Key Technical Decisions

- KTD24. **Provisioning uses a versioned desired-state manifest and an append-only operation ledger.** The manifest has a schema version, organization/incident stable keys, deployment/environment, geography, locale, module/provider profiles, catalogs, access policy, resource names, and desired lifecycle state. A planner compares desired and observed state. Apply executes dependency-ordered idempotent operations with checkpoints and resource ownership tags. Secrets are referenced by name/version, never stored in the manifest or ledger. Destructive or public-routing operations require a second approval. Cites R23-R26.
- KTD25. **Signal ingestion preserves immutable observations and mutable canonical interpretations.** `signal_sources` describes adapters and trust/health policy; `source_observations` stores normalized, versioned provider claims plus a checksum and protected raw-object reference; `hazard_events` is the current canonical correlation; `hazard_event_observations` records membership and correlation version. Provider revisions append observations or versions; they do not erase the evidence used by a prior decision. Cites R27-R31.
- KTD26. **Correlation is deterministic, replayable, and separated from policy.** Adapter normalization, event correlation, candidate policy, and provisioning are four separate stages. Correlation produces scored reasons and stable canonical event IDs from versioned rules. It cannot activate incidents. A replay writes to an isolated run, compares outcomes, and requires approval before replacing current correlations or candidates. Cites R27-R31.
- KTD27. **Source confidence is provenance, not truth.** Each adapter records authority class, coverage, known latency, and health. Candidate policy can require one authoritative source or corroboration, but disagreement remains visible. Source silence, timeout, or circuit-open state cannot close, downgrade, or withdraw an event. Withdrawal and revision are explicit observations. Cites R28-R31.
- KTD28. **Candidate review is a capability-gated state machine.** `incident_candidates` references a canonical hazard event and proposed organization/geography/profile. `candidate_decisions` is append-only and records actor, transition, reason, rule version, evidence IDs, and timestamp. `incident:detect-review` can reject/suppress/merge; `incident:provision` can approve preview; `incident:activate` is a separate capability and approval. No transition trusts a client-supplied tenant ID. Cites R9, R23-R32.
- KTD29. **Public activation is a two-phase commit across platform and edge state.** Prepare creates an isolated preview, validates all dependencies, records immutable artifacts, and keeps producers/notifications/public routes off. Commit attaches the approved hostname and enables only the manifest's resources. If commit verification fails, routing returns to the prior deployment and the new incident stays `ready` or `paused`; database evidence and provisioning ledger remain for resume. Cites R19-R21, R24-R26, R32.
- KTD30. **Configuration-specific public builds are a bootstrap state, not the target.** U23 initially preserves today's `config/deployment.config.json` build path so provisioning can ship safely before U28. U28 then moves non-secret public deployment identity into a trusted runtime bootstrap and proves one immutable artifact across domains. The admin remains an authenticated app with separately configured platform and organization deployments. Backend hostname/CORS authority is still promoted before route attachment, and every served bootstrap/artifact/config digest is recorded. Cites R19, R23-R26, R45-R47.
- KTD31. **Platform-operator and organization-admin authority are separate trust domains.** The operator CLI/protected runner is the bootstrap, break-glass, and canonical reconciliation executor. U30 adds an internal Mallanet operations UI only after that executor is stable; it calls the same plan/apply/approval APIs and never invents a second mutation path. The organization admin is separately deployed/authorized and cannot create organizations, claim hostnames, activate public traffic, or select unrelated organizations. U23 replaces the current globally unique-user/nullable-`org_id` shortcut with memberships before organization two. No global/NULL seed administrator silently inherits a new organization. Cites R9, R10, R23-R26, R51-R58.
- KTD32. **Unautomatable external work is a durable state, not a skipped step.** DNS, custom-domain attachment, Access, or secret operations that current credentials cannot perform enter `waiting_external`, emit exact redacted instructions, and poll/verify observed state before resume. The planner never claims full automation and activation cannot bypass an external checkpoint. Cites R23-R26.
- KTD33. **The existing earthquake API remains a compatibility projection.** The USGS adapter fetches once and dual-writes immutable observations plus the current `earthquakes` read model. `/api/earthquakes`, `{ earthquakes, sync: { fetchedAt } }`, map behavior, cache semantics, and both scheduler transports remain compatible. Ingestion-run health becomes the operational freshness source; correlation/candidate flags can be disabled without stopping the public catalog. Retire the legacy projection only after parity and the complete client/cache/rollback window. Cites R5, R20, R21, R27-R31.
- KTD34. **Hazard adapters are hostile-input boundaries.** Runtime schemas validate every payload. Fetchers enforce HTTPS, provider-host allowlists, content type, maximum bytes, redirect policy, timeout, bounded retry/jitter, and circuit behavior. Provider detail URLs are not followed unless reconstructed or allowlisted. Cursors advance only after durable run/observation commit. Raw payloads, query URLs, credentials, and tokens never enter logs. Cites R27, R28.
- KTD45. **The public frontend bootstrap is host-authoritative, signed/versioned, and non-secret.** An edge/bootstrap endpoint resolves an exact canonical hostname through the deployment authority created in U9/U23 before any CDN or Upstash lookup, returns only approved public configuration, and includes deployment ID, allowed/default incidents, config revision/digest, API authority, asset/PWA metadata, and cache epoch. HTML and bootstrap use bounded caching and explicit revalidation under the base plan's KTD56-KTD60/U34 cache contract; unknown host, digest mismatch, stale assignment, or untrusted API origin fails closed. Query/header incident overrides can select only among the deployment's public incident set and are never backend authority. Sensitive/admin/support state is never cached. Cites R45-R47.
- KTD46. **Deployment assignment and incident scope are different records.** A `deployment_incidents` relation pins visible incidents, order, featured/default state, validity, and configuration revision. Normal APIs still accept one server-resolved `TenantScope`; explicitly contracted aggregate/read-model endpoints perform bounded cross-incident reads and return only approved public/aggregate fields. A frontend incident switch clears scoped state and obtains fresh authority; it does not mutate a global singleton tenant. Cites R8, R9, R45-R47, R58.
- KTD47. **Channel provisioning extends the U23 desired-state saga.** `communication_channels`, immutable channel revisions, provisioning steps, verification samples, and activation decisions record automated and external resources. Provider adapters expose `plan`, `apply`, `observe`, `verify`, `pause`, and `retire` where supported; manual steps expose exact instructions plus observed-state evidence. Manifests carry secret references only. Channel IDs, sender identities, invite URLs, webhook endpoints, templates, consent purposes, moderation ownership, cost limits, and environment cannot be shared implicitly across incidents. Cites R48-R50.
- KTD48. **Communications enable in ordered safety gates.** Public contact/discovery links can activate after verification. Inbound webhooks/forms then enable with authentication, replay protection, schema validation, tenant resolution, rate limits, and moderation routing. Outbound transactional/template messaging enables after consent/template/provider verification. Broadcast/mass messaging requires a separate approval, audience freeze, preview/count, rate/cost limits, stop switch, delivery audit, and opt-out handling. Failure pauses that channel without changing incident routing. Cites R24-R26, R48-R50, R55.
- KTD49. **Authorization is a fixed-scope capability model over global identity plus independent organization memberships.** Keep `users` as global identity; add `organization_memberships` with one initial org role per membership, and attach tenant grants to membership—not bare user—so suspending organization A neither revokes nor leaks B. Role templates are reusable definitions, not authority until instantiated/assigned in an organization. A grant stores subject membership, capability, one scope type/ID, environment, validity interval, grantor, reason/reference, version, and revocation. A registry declares each capability's allowed scope types and whether it applies to `self` or named descendants; the evaluator accepts `(AuthContext, capability, targetScope)` and verifies ancestry in the database. Deployment and incident are peers: neither grant implies the other's authority. Platform operator assignments use a separate table/trust domain; API keys remain organization/incident pinned. Cites R10, R22, R51-R54.
- KTD50. **Administration has two deployed authorities that can share code but not ambient access.** `ops.mallanet` (or equivalent) is the platform operations surface with higher assurance and platform sessions; organization admin hosts accept only organization membership and incident/deployment grants. Shared contracts/components are encouraged, but cookies, BFF authority, cache keys, API audiences, CSP/connect-src, and deep-link resolution remain separate. Neither UI obtains rights by passing a different org/incident ID. Cites R51-R54, R57.
- KTD51. **Admin mutations delegate to domain operation ledgers.** U30/U31 present and approve U23/U26/U29 plans, release records, privacy operations, and domain commands; they do not directly mutate Cloudflare/provider resources or bypass state machines. Every high-impact action has preview/diff, expected-version compare-and-swap, idempotency key, actor/scope/build, result, and rollback/next action. Read dashboards are derived projections and expose staleness/source health. Cites R23-R26, R53-R55.
- KTD52. **Support access is an explicit session object, never impersonation.** A support grant references the operator, ticket/reason, exact organization and optional incident, allowlisted capabilities, approver, issue/expiry/revocation times, and visible audit/banner state. It issues a short-lived `tenant-support` audience credential; exact TTL/revocation is checked from the database on every privileged request. Read-only is the default and write elevation names exact capabilities with a shorter TTL. It cannot create API keys, change membership/roles/grants, reveal secrets, export PII, change deployment/hostname state, or grant more support access unless a separately defined higher policy permits it. The organization can view/revoke sessions. Break glass requires stronger authentication, notification, shortest TTL, and after-action review. Expiry/revocation terminates active use and invalidates cached/admin state. Cites R52, R56-R58.
- KTD53. **Approval is a durable policy decision, not a UI confirmation.** `approval_requests` pin operation kind, target scope, immutable plan/config/audience/result digest, risk class, requester, required approver classes/count, expiry, and decision records. Person-level, family, evidence, contact, and confidential case data are never made discoverable by the portfolio UI. A named cross-scope workflow uses no-store responses, explicit participating scopes/purpose, result bounds, and sensitive access events. Cites R39, R43, R53, R58.

Secret fields accept only a secret reference plus expected version/metadata.

  1. Validate schema and canonical stable keys offline.
  2. Resolve the target environment and refuse production when the command lacks an explicit production flag and approval record.
  3. Read observed database and Cloudflare/config state without mutation.
  4. Produce a deterministic plan grouped into database-expand, identity/access, provider/config, async resources, preview deployment, data/catalog seed, readiness, and public activation.
  5. Flag destructive, replacement, hostname reassignment, secret rotation, notification, and cost-producing operations for separate approval.
  6. Persist the approved plan digest before apply; refuse if observed state changed since planning.
  7. Create organization and draft incident rows first. Do not attach public authority.
  8. Create incident-scoped catalogs, module/provider/channel desired state, the U30 organization membership/role assignments, and one expiring one-use initial-owner invitation. Require recovery contacts and never fall back to a global/NULL-org seed administrator or infer platform authority.
  9. Provision or validate preview-only edge/config resources. Keep Queue/Cron producers, outbound notifications, and public routes disabled.
  10. Before U28, build configuration-specific immutable frontend/admin artifacts. After U28, assign the immutable public artifact to the deployment revision and build/configure only the organization admin authority. In both modes, promote compatible backend CORS/hostname authority before preview route attachment and record served artifact/bootstrap/config digests. Seed only incident-owned reference data.
  11. Run readiness: schema capability, hostname authority, two-tenant isolation, cache/rate-limit partition, auth/capabilities, module discovery, provider no-op/live checks, browser storage namespace, Queue/Cron dry-run, accessibility and critical-flow smoke.

Multiple incidents can be active for one organization through one or more deployments. `failed` and `paused` are non-public or use the approved holding/read policy and are producer-off. `closed` is read-only under incident retention policy. `archived` keeps retention/legal holds, revokes write credentials, removes schedules only after backlog/decoder checks, and retains a tombstone preventing stable-key reuse. Reassignment uses the base plan's KTD58/KTD59 cache epoch and invalidation rules plus KTD29 activation.

A failed external resource step is retried with the same idempotency key. Unknown partially created resources are quarantined for operator adoption or deletion; they are never guessed. ### U24. Hazard signal ingestion and source health

- **Goal:** turn the current USGS-specific catalog poller into the first adapter of a provider-independent, replayable signal-intelligence pipeline without changing Colombia's public earthquake response.
- **Requirements:** R27-R29, R31.
- **Dependencies:** U7, U14, U20. U24 implements KTD35's shared provenance value contract in hazard-owned tables; it does not depend on Family Search storage or U27.

### U25. Hazard-event correlation and incident-candidate review

### U30. Organization membership and tenant authorization conversion

- **Goal:** replace today's global/nullable organization authorization and wildcard system-role behavior with global login identities plus independent, server-settled organization memberships before a second organization exists.
- **Requirements:** R10, R22, R51, R52, R54, R57; applies KTD8, KTD31, KTD49, KTD50, KTD54.
- **Dependencies:** U7, U9, U10, U11. This is a hard U23 organization-two and U21 cutover gate.
- **Repository evidence:**

  | Location | Current behavior |
  |---|---|
  | `infra/db/schema.ts` | documents NULL organization as global |
  | `backend/src/auth/resolve.ts` | grants wildcard authority to system roles and resolves roles/grants without organization filtering |
  | `backend/src/auth/seed.ts` | creates/promotes NULL-org superadmins |
  | invitations | write `orgId: null` and acceptance overwrites the user's single global role |
  | users | have one `role_id`/`org_id` and globally unique email |
  | API keys | lack organization/incident ownership |
  | admin BFF | forwards a cookie to one backend and cannot make a browser org header authoritative |
- **Files:** `infra/db/schema.ts` and journal migrations; `packages/contracts/src/admin-auth.ts`; `backend/src/auth/{jwt,resolve,seed,capabilities,audit}.ts`; auth middleware; auth/users/roles/grants/API-key services/routes/resources; admin auth/BFF/invite/user/role/grant/API-key/audit surfaces; membership/isolation/mixed-version tests; and an authorization migration/rollback runbook.
- **Data model:** keep `users` as globally unique login principals. Add `organization_memberships(user_id, organization_id, status, role_id, sponsor, starts_at, expires_at, activated/suspended/ended_at, version)` unique by user/org. Roles are organization-owned and a role belongs to the membership's organization. Re-key individual grants to membership with capability, fixed target scope, environment, interval, grantor/reason/reference/delegation ceiling, version/revocation. Invitations bind organization, role/template, inviter membership, intended email, one-use nonce, expiry, and acceptance state. API keys gain membership/organization/incident/environment/credential version and prohibited endpoint classes.
- **Migration procedure:**
  1. Inventory every user, role, role capability, grant, invitation, API key, `is_system`, `is_super_admin`, and NULL organization plus recent effective use. Freeze creation of new legacy-global authority during conversion.
  2. Expand membership/grant/invitation/API-key schema and build scoped repositories/evaluator without removing legacy fields. The JWT remains a global `sub`; per-org admin host/config settles organization server-side, then selects one active membership. Browser org headers are ignored as authority.
  3. Add a capability-scope registry and test every legal/illegal combination. Organization governance may reach descendants only for named capabilities; deployment and incident never inherit from each other. Draft incidents without a deployment remain selectable only through a valid incident grant.
  4. Backfill Colombia through an explicit reviewed mapping. Map operational rights to the Colombia incident and governance rights to the Colombia organization. Never convert `is_system`, `is_super_admin`, or NULL organization into platform authority. Require attestation for initial owners and at least two recovery contacts before tighten.
  5. Run legacy and scoped evaluators in shadow mode; record differences without sensitive inputs. Investigate every widening and every loss that would lock out an approved operator.
  6. Deploy the scoped backend first and prove old admin compatibility. Move admin/BFF `/me`, queries, mutations, invitations, and selector to server-settled membership context. Invitation acceptance atomically consumes the token, upserts identity, and creates/activates only that organization's membership.
  7. Convert API keys and machine actors; keys are incident/environment pinned and cannot administer memberships/roles/grants/invitations/platform/support/deployments/hostnames regardless of textual scopes.
  8. Enforce non-NULL organization ownership, remove system/wildcard authorization and seed promotion, return explicit effective capabilities instead of `*`, and block the last-owner removal. Then and only then permit organization two.
  9. Advance the rollback floor: no old backend/workflow that understands only global role/org fields remains promotable after organization two. Retire legacy fields/reads in a later compatibility release.
- **Contingencies:** mapping uncertainty blocks that principal and requires owner review; it never defaults wider. Lockout keeps the prior scoped-compatible version and a separately governed recovery path—not the wildcard. Invitation partial failure commits neither membership nor token consumption. Membership suspension invalidates only that organization and is checked fresh/version-keyed on the next request. A mixed-version widening, NULL grant, wildcard response, or foreign-ID success is a release stop.
- **Test scenarios:** same email in organizations A/B with different roles; password reset preserves both; forwarded/wrong-user/reused/concurrent invite; role-org mismatch; forged org/scope headers; foreign user/role/grant/key/incident IDs; draft incident selection; deployment/incident sibling non-inheritance; grant start/expiry/revoke in open tab; last owner; suspension in A while B works; API key incident mismatch/prohibited admin endpoints; old-admin/new-backend and new-admin/compatible-backend; `/me` no wildcard; Colombia legacy superadmin no access to B; no active NULL/global grant.
- **Verification:** a generated authorization matrix covers every capability/scope/credential kind. Shadow differences are human-attested. Two global test identities each hold two distinct memberships. Revocation/expiry is immediate. Organization-two creation remains mechanically blocked until the wildcard/rollback sentinels pass.
